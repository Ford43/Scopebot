# ผลตรวจ RAG ของ bot_bea29390 — 6 พฤศจิกายน 2026

## ขอบเขต

อ่านดัชนีที่บอทประกาศใช้งานจริงและไฟล์ food_menu.txt ใช้โมเดล Ollama จริงในเครื่อง ไม่ส่งข้อความ LINE ไม่บันทึกประวัติสนทนา ไม่ ingest หรือเปลี่ยน .env ทดสอบด้วยประวัติว่าง จึงไม่ใช่การจำลองประวัติแชทเดิมทั้งหมด สคริปต์และผลดิบอยู่ในโฟลเดอร์เดียวกัน

โมเดลใช้งานเดิม qwen2.5:1.5b; reranker BAAI/bge-reranker-v2-m3 บน CPU; เกณฑ์ 0.35 เครื่องมี GTX 1650 VRAM 4 GB การทดสอบ 7b รายงานจาก ollama ps ว่าใช้ CPU/GPU 55%/45%, ขนาดโหลด 5.1 GB, context 4096

## สิ่งที่พิสูจน์ได้

1. คำถาม “ขอรายละเอียดอาหารจานหลัก” จบก่อนเรียกโมเดลสร้างคำตอบในระบบจริง ตัวค้นหาหาผู้สมัคร 27 ชิ้น แต่ reranker ตัดทั้งหมด คะแนนสูงสุด 0.207 ต่ำกว่า 0.35 เอกสารอันดับแรกเป็นแกงเขียวหวานซึ่งอยู่หมวดต้มและแกง การลด threshold อย่างเดียวเสี่ยงนำคนละหมวดมาตอบ
2. ข้อมูลหมวดสูญเสียความสัมพันธ์ระหว่างแบ่งข้อความ: หมวดอาหารจานหลักกลายเป็นหน่วยแยก ส่วนชื่ออาหาร ราคา รายละเอียดแยกเป็นหลายหน่วยโดยไม่มีหมวดแม่ และบรรทัดหมวดถัดไปถูกผูกกับหัวข้ออาหารก่อนหน้า ดู menu-segmentation.json
3. เมื่อทดลองเก็บข้อมูลครบหมวดในหน่วยความจำ คะแนนหมวดอาหารจานหลักเพิ่มเป็น 0.768; หมวดอื่นสูงสุด 0.059 แต่ของหวานที่ตรงคำถามได้ 0.293 จึงยังตกเกณฑ์ แสดงว่าต้องประเมิน retrieval ต่อ ไม่ควรถือคะแนนเป็นความน่าจะเป็นความถูกต้อง
4. ข้อมูลครบอย่างเดียวยังไม่พอ: เมื่อใช้ prompt/schema/ตัวตรวจเดิม 1.5b ตอบซ้ำคำถามพร้อมเลขอ้างอิงซ้ำ ตัวตรวจปฏิเสธ unsupported_claim อย่างถูกต้อง การย่อ prompt แต่คง schema เดิมทำให้ตอบรายชื่อ 3 เมนู แต่ evidence_ids ว่าง จึงถูกปฏิเสธ unsupported_evidence อย่างถูกต้อง
5. 1.5b สามารถตอบครบและถูกจากเมนูเมื่อใช้คำสั่งข้อความธรรมดาที่เรียบง่าย แต่การทดลองนี้เปลี่ยนทั้งรูปแบบเอกสารและ prompt/รูปแบบผลลัพธ์ จึงใช้ยืนยันได้เพียงว่ามันมีความสามารถตอบกรณีนี้ ไม่ใช่ผลทดสอบระบบเต็มหรือหลักฐานว่าแก้ prompt อย่างเดียวพอ
6. ทดลอง 7b ด้วยหมวดเดียวกันและ prompt/schema เดิม ยังตอบไม่พบข้อมูลในหนึ่งรอบ จึงไม่มีหลักฐานให้เปลี่ยนโมเดลทันที
7. คืนข้อความต้นฉบับหมวดอาหารจานหลักครบทั้งหมวดผ่าน validate_grounded_answer เดิม (True, None) ได้ เป็นการตรวจ validation แบบแยกส่วน ยังไม่ได้ติดตั้งเส้นทางตอบนี้หรือพิสูจน์ครบทุกหมวด

## ลำดับงานที่ควรทำต่อ

1. รักษาหมวดแม่และรายการย่อยพร้อมราคา/รายละเอียดในข้อมูลที่จัดทำดัชนี และเพิ่มการทดสอบเมนูหลายหมวดไม่ให้ปะปนกัน การใช้งานจริงต้อง rebuild เฉพาะบอทเป้าหมายหลังตรวจการแก้ไขแล้ว
2. รองรับคำถามขอรายละเอียดทั้งหมวดและดึงหมวดให้ครบ เมื่อระบุหมวดได้แน่นอน ให้ตอบข้อความจากเอกสารพร้อม citation โดยตรงเพื่อลดการพึ่งการสร้าง JSON ของโมเดล เก็บการตรวจข้อเท็จจริงไว้
3. วัดและปรับการคัดกรองด้วยชุดคำถามหลายประเภท รวมคำถามที่ไม่มีคำตอบและหมวดใกล้กัน ห้ามลด threshold ทั่วระบบจากตัวอย่างเดียว
4. หลังระบบส่งหลักฐานถูกและครบ ค่อยเปรียบเทียบ 1.5b/7b ด้วยชุดคำถามเดียวกันหลายรอบ แยก warm/cold และประเมินความครบถ้วน ความถูกต้อง citation การปฏิเสธคำถามนอกข้อมูล และเวลา ไม่เปรียบเทียบเฉพาะคำตอบที่ระบบยอมปล่อยผ่าน
5. โหลดโมเดลล่วงหน้าช่วยเวลาครั้งแรก แต่ไม่แก้คุณภาพ retrieval และต้องประเมิน RAM/VRAM กับการใช้งานพร้อมกัน
