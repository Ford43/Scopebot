# ScopeBot — สไลด์เสริมเชิงเทคนิค

รวมประมาณ 8 นาที ใช้ทุกหน้าหรือเลือกตามเวลาที่มี

## 1. Deployment

เวลาแนะนำ 2 นาที
ภาพนี้อธิบายรูปแบบติดตั้งตาม docker-compose.yml และ docker-compose.tunnel.yml ไม่ได้ยืนยันว่าเครื่องที่นำเสนอเปิดบริการทั้งหมดนี้อยู่แล้ว Browser และ LINE ติดต่อ public hostname ของ Cloudflare ผ่าน HTTPS ตัว cloudflared ใน Docker เปิดการเชื่อมต่อ Tunnel และส่งต่อคำขอเข้า Nginx ที่ service frontend:80 Nginx ให้ไฟล์ React และ proxy /api ไป FastAPI ที่ api:8000 ภายใน container ของ API มีโค้ด RAG และเชื่อม PostgreSQL ที่ db:5432 ส่วน Ollama ตาม compose รันบน host ที่พอร์ต 11434 โดย API ใช้ host.docker.internal เพื่อเข้าถึง มี volumes เก็บ PostgreSQL เอกสาร และ Chroma ให้คงอยู่หลังสร้าง container ใหม่ การใช้ Qdrant มี compose ทางเลือกและไม่ได้แสดงในภาพนี้
ตอบฝ่ายไอที: การเปิดพอร์ต การสำรองข้อมูล การจัดสรร RAM/CPU/GPU และการเก็บ log ต้องประเมินตามสภาพแวดล้อมจริง ไม่สรุปว่า production-ready จากการมี Docker เพียงอย่างเดียว
อ้างอิง: docker-compose.yml; docker-compose.tunnel.yml; deploy/nginx.conf; deploy/DEPLOY.md

## 2. วงจรเอกสาร

เวลาแนะนำ 2 นาที
เมื่อเจ้าของบอทเปลี่ยนเอกสาร ระบบบันทึก revision และเข้าคิวงาน สร้าง snapshot จากเอกสารที่กำหนดให้บอท แล้วสร้างดัชนีใหม่แยกจากชุดที่กำลังให้บริการ ตรวจข้อความที่จัดเก็บ ก่อนเผยแพร่ path ของดัชนีใน transaction ถ้ามีเอกสารเปลี่ยนระหว่างสร้าง revision จะป้องกันงานเก่าเผยแพร่ทับงานใหม่
จุดสำคัญคือเพิ่มเอกสารกับถอนข้อมูลทำงานต่างกัน การเพิ่มยังใช้ published index เดิมได้ ถ้าเพิ่มล้มเหลวจะไม่แทนชุดที่ใช้งานอยู่ แต่การแทนที่หรือลบจะบล็อกการตอบจนสร้าง revision ปัจจุบันสำเร็จ เพื่อไม่ใช้ข้อมูลที่ถอนออกแล้ว บอทที่ยังไม่มีดัชนีใช้ได้จะยังตอบจากเอกสารไม่ได้ สถานะมี idle, queued, processing, ready, error และ has_usable_knowledge เป็นตัวกำหนดความพร้อมแยกต่างหาก เอกสารอ่านไม่ได้ทำให้ candidate build ล้มเหลวทั้งชุด ไม่รายงานว่าสำเร็จทั้งที่นำเข้าได้บางส่วน
อ้างอิง: docs/knowledge-updates.md; docs/rag-correctness.md

## 3. กรณีผิดพลาด

เวลาแนะนำ 2 นาที
กรณีแรก RAG ไม่มีหลักฐานที่ตอบได้ Web แสดงข้อความและ offer_handoff ส่วน LINE webhook ปัจจุบันส่งการ์ด CONTACT_FLEX ให้เลือกติดต่อ ผู้ใช้กดหรือส่งคำขอติดต่อแล้วจึงเข้า waiting ไม่ควรอธิบายว่าทุกช่องทางเข้าคิวเองทันที ต้องแยกจาก chat API ที่รับ source_channel อื่นและอาจมีเงื่อนไข auto-handoff
กรณีบริการสร้างคำตอบหรือค้นหาขัดข้อง RagUnavailableError จะใช้ข้อความ RAG_ERROR_MESSAGE ว่าขออภัย ระบบขัดข้อง กรุณาลองใหม่อีกครั้ง เว็บมี offer_handoff และ response_status=error ส่วน LINE ส่งข้อความ error ไม่สวมเป็นคำตอบจากเอกสาร การทำงานในแต่ละ failure point อาจมี fallback ตาม semantic pipeline จึงไม่ใช่ว่า error เล็กน้อยทุกตัวต้องทำให้ตอบไม่ได้
กรณีรอคน ระบบบันทึกข้อความ ผู้ใช้ได้รับข้อความแจ้งให้รอ พอเจ้าของบอทตอบจึงเป็น human ไม่มีการรับรองเวลาตอบของเจ้าหน้าที่ในสไลด์นี้
อ้างอิง: api/routers/chat.py; api/routers/line_webhook.py; api/routers/live_chat.py; rag/rag_pipeline.py

## 4. การประเมินเชิงลึก

เวลาแนะนำ 2 นาที
แจ้งก่อนว่าหน้านี้เป็นตัวอย่างอธิบายเกณฑ์ที่อิงเงื่อนไขใน test/test_rag_correctness.py ไม่ใช่ผลจากการรันโมเดลจริงหรือการวัด accuracy ใหม่ เอกสารตัวอย่างมีเพียงนโยบายรับคืนสินค้าชำรุด กรณีตอบถูกต้องรักษาข้อจำกัดนี้และอ้างอิงให้ตรง กรณีตอบไม่ครบตัดคำว่าชำรุดออก แม้ประโยคส่วนที่เหลือจะอยู่ในต้นฉบับก็ทำให้ความหมายกว้างเกินหลักฐาน ต้องไม่ยอมรับ ส่วนการถามค่าจัดส่งเป็นข้อมูลที่เอกสารตัวอย่างไม่มี การปฏิเสธจึงเหมาะสม
สิ่งที่เรียนรู้คือไม่ควรให้คะแนนจากความลื่นไหลเพียงอย่างเดียว ต้องดูความครบถ้วน ความรองรับจากหลักฐาน และความถูกต้องของ citation เมื่อประเมินจริงให้มีคำถามมีคำตอบ ไม่มีคำตอบ เงื่อนไขซับซ้อน และคำถามต่อเนื่อง บันทึกโมเดล เอกสาร รุ่นระบบ และเวลา แยก retrieval failure จาก generation/grounding failure แล้วรายงานตามข้อมูลที่เก็บได้
อ้างอิง: test/test_rag_correctness.py (cropped restrictions และ invented assertions); docs/rag-correctness.md; docs/semantic-search.md
