## 1. Title — ScopeBot

เวลา 30 วินาที

### เนื้อหาบนสไลด์
แพลตฟอร์มแชตบอตสำหรับองค์กร
ตอบคำถามจากเอกสารด้วย RAG
รองรับ Web, LINE และการส่งต่อให้คน

### ภาพและตำแหน่ง
ด้านขวา: โลโก้ ScopeBot หรือภาพหน้าจอหลัก
ใต้ชื่อโครงการ: ชื่อสมาชิกและสถาบันจริง

### บทพูด
สวัสดีคณะอาจารย์และทีมไอทีทุกท่าน วันนี้ขอนำเสนอ ScopeBot ระบบแชตบอตสำหรับองค์กรที่นำเอกสารมาใช้เป็นแหล่งความรู้ในการตอบคำถาม ผู้ดูแลสามารถสร้างบอทและกำหนดเอกสารให้เหมาะกับงานได้ ระบบรองรับการสนทนาผ่านเว็บและ LINE รวมถึงการให้เจ้าหน้าที่รับช่วงต่อ การนำเสนอจะเริ่มจากปัญหา ภาพรวมทางเทคนิค และการสาธิต ก่อนสรุปผลทดสอบกับข้อจำกัดของระบบ

ประโยคเชื่อม: เริ่มจากปัญหาที่เราต้องการแก้ก่อน



## 2. The Problem — ปัญหาขององค์กรยุคปัจจุบัน

เวลา 60 วินาที

### เนื้อหาบนสไลด์
ข้อมูลอยู่ในหลายไฟล์และค้นหาได้ยาก
เจ้าหน้าที่ต้องตอบคำถามเดิมซ้ำ
คำตอบอาจขาดบริบทหรือข้อมูลอ้างอิง
ผู้ใช้ต้องการช่องทางเข้าถึงข้อมูลที่สะดวก

### ภาพและตำแหน่ง
ด้านขวา: ภาพเอกสารหลายแหล่ง
ประกอบคำถามสมมติ เช่น “ต้องใช้เอกสารอะไรบ้าง”
หลีกเลี่ยงข้อมูลส่วนบุคคล

### บทพูด
ปัญหาที่โครงงานนี้มุ่งแก้คือ ผู้ใช้อาจมีคำถามสั้น ๆ แต่ข้อมูลคำตอบอยู่ในเอกสารหลายหน้า หรือกระจายอยู่หลายไฟล์ จึงต้องรู้ก่อนว่าควรเปิดเอกสารไหนและอ่านตรงส่วนใด ขณะเดียวกันเจ้าหน้าที่อาจต้องตอบคำถามลักษณะเดิมอยู่บ่อยครั้ง ตัวอย่างสถานการณ์สมมติคือ ผู้ใช้ถามว่าต้องเตรียมเอกสารอะไรบ้างสำหรับขั้นตอนหนึ่ง คำตอบอาจอยู่ในคู่มือ แต่ผู้ใช้ไม่รู้ชื่อไฟล์ ScopeBot จึงออกแบบให้ผู้ใช้ถามเป็นภาษาปกติ แล้วระบบค้นข้อความที่เกี่ยวข้องมาช่วยตอบ เป้าหมายของเราคือทำให้เข้าถึงข้อมูลสะดวกขึ้น ส่วนการลดเวลาหรือภาระงานเป็นประโยชน์ที่ต้องวัดกับการใช้งานจริงต่อไป

ประโยคเชื่อม: จากปัญหานี้ เรากำหนดขอบเขตของระบบไว้ดังนี้



## 3. The Solution & Value Proposition — ทางออกและคุณค่าของ ScopeBot

เวลา 70 วินาที

### เนื้อหาบนสไลด์
ค้นความรู้จากเอกสารของแต่ละบอท
แสดงแหล่งข้อมูลประกอบคำตอบบนเว็บ
จัดการหลายบอทผ่านแพลตฟอร์มเดียว
ส่งต่อเจ้าของบอทเมื่อผู้ใช้ต้องการคนช่วย

### ภาพและตำแหน่ง
ด้านขวา: ภาพคำตอบพร้อมแหล่งอ้างอิง
เน้นชื่อไฟล์หรือข้อความหลักฐาน
ประโยชน์ด้านเวลาต้องประเมินจากการใช้งานจริง

### บทพูด
คุณค่าที่เสนอคือการเข้าถึงข้อมูลผ่านบทสนทนา การตรวจสอบแหล่งข้อมูล และการจัดการบอทอย่างเป็นระบบ ประโยชน์ด้านเวลาหรือภาระงานยังต้องวัดกับผู้ใช้จริง ไม่กล่าวเป็นผลที่พิสูจน์แล้ว

## 5. System Architecture — โครงสร้างระบบ

เวลา 100 วินาที

### เนื้อหาบนสไลด์
React / TypeScript: หน้าจอเว็บ
FastAPI: ตรวจสิทธิ์และควบคุมงาน
PostgreSQL: บัญชี บอท และประวัติ
Chroma / Qdrant + Ollama: งาน RAG

### ภาพและตำแหน่ง
ด้านขวา: แผนภาพ Web / LINE เชื่อม FastAPI
แยกเส้นไป PostgreSQL, Storage และ RAG
RAG เชื่อม vector store และ Ollama
ระบุ vector backend ที่ตั้งค่าใช้งานจริง

### บทพูด
ในด้านสถาปัตยกรรม ฝั่งเว็บพัฒนาด้วย React เป็นส่วนที่ผู้ใช้เห็นและใช้จัดการบอท เมื่อผู้ใช้ส่งคำขอ Frontend จะติดต่อ FastAPI ซึ่งเป็นศูนย์กลางการประมวลผล Backend ตรวจตัวตนและสิทธิ์ก่อนเข้าถึงข้อมูล จากนั้นจึงเลือกว่าจะอ่านหรือเขียนฐานข้อมูล หรือเรียกกระบวนการ RAG สำหรับตอบคำถาม PostgreSQL เก็บข้อมูลที่มีโครงสร้าง เช่น บัญชี บอท และประวัติการสนทนา ส่วนข้อความจากเอกสารและ embeddings สำหรับค้นหาอยู่ใน ChromaDB จากนั้น Ollama ทำหน้าที่ให้บริการโมเดลภาษา สำหรับ LINE คำขอเข้าผ่าน webhook ที่ Backend และมีการตรวจ signature ตามช่องทางนั้น ในรูปแบบการติดตั้งที่มีในโครงการ Nginx ให้บริการหน้าเว็บและส่งคำขอ API ไปที่ FastAPI มี Docker Compose ช่วยจัดบริการ ส่วน Ollama รันบนเครื่อง host ตามการตั้งค่า compose ความสามารถรองรับโหลดจริงยังต้องประเมินตามเครื่องและโมเดลที่เลือก

ประโยคเชื่อม: ส่วนที่ทำให้คำตอบเชื่อมโยงกับเอกสารคือกระบวนการ RAG



## 6. The RAG Core Process — กระบวนการ RAG

เวลา 120 วินาที

### เนื้อหาบนสไลด์
เตรียมเอกสาร: แบ่งข้อความและทำ embeddings
ค้นข้อมูล: ใช้คำถามและบริบทล่าสุด
จัดอันดับหลักฐานด้วย semantic reranking
สร้างคำตอบและตรวจหลักฐานกับ citation

### ภาพและตำแหน่ง
ด้านขวา: แผนภาพ 2 แถว
เอกสาร → chunks → embeddings → index
คำถาม → ค้นหา → rerank → ตอบและตรวจหลักฐาน
แสดงชื่อไฟล์หรือเลขหน้าเมื่อมีข้อมูล

### บทพูด
ระบบปัจจุบันรองรับ semantic retrieval โดยใช้คำถามก่อนหน้าช่วยตีความคำถามต่อเนื่อง แล้วค้น candidate passages และจัดอันดับด้วย reranker ก่อนตรวจ citation กับข้อความหลักฐาน คำตอบเก่าของบอทไม่ถือเป็นข้อเท็จจริงจากเอกสาร คะแนน reranker เป็นคะแนนความเกี่ยวข้อง ไม่ใช่ความน่าจะเป็นที่คำตอบถูกต้อง

RAG เป็นกระบวนการนำข้อมูลที่ค้นพบมาเป็นบริบทให้โมเดลภาษา โดยมีสองช่วงสำคัญ ช่วงเตรียมความรู้เริ่มจากอ่านไฟล์และแบ่งเนื้อหาออกเป็นข้อความย่อยหรือ chunks จากนั้นแปลงข้อความเป็น embeddings ซึ่งเป็นตัวแทนเชิงตัวเลขที่ใช้ค้นหาข้อความที่เกี่ยวข้อง แล้วเก็บไว้ในดัชนีของบอท ขั้นตอนนี้เป็นการเตรียมความรู้สำหรับการค้นหา เมื่อเอกสารเปลี่ยน ระบบจึงต้องประมวลผลดัชนีที่เกี่ยวข้องให้ตรงกับข้อมูลใหม่

ช่วงตอบคำถามเริ่มเมื่อผู้ใช้ส่งข้อความเข้ามา ระบบใช้คำถามและบริบทคำถามล่าสุดช่วยค้นเนื้อหาที่เกี่ยวข้อง จากนั้นนำข้อความที่ค้นได้มาเป็นหลักฐานประกอบคำสั่งให้โมเดลสร้างคำตอบ ตัวอย่างสมมติคือถามว่าเงื่อนไขการใช้บริการมีอะไรบ้าง ระบบจะค้นส่วนเงื่อนไขในเอกสารก่อน จึงไม่ต้องส่งเอกสารทั้งหมดให้โมเดลทุกครั้ง โค้ดปัจจุบันมีการตรวจหลักฐานของคำตอบ และสามารถปฏิเสธข้อความที่ไม่มีข้อมูลรองรับได้ ส่วนเว็บสามารถแสดงชื่อไฟล์และข้อความประกอบให้ตรวจสอบย้อนกลับ แต่ไม่ได้หมายความว่าคำตอบทุกกรณีจะถูกต้องเสมอ การประเมินจึงต้องดูทั้งค้นข้อความถูกหรือไม่ และคำตอบรักษาความหมายกับเงื่อนไขในเอกสารครบหรือไม่

ประโยคเชื่อม: นอกจากความถูกต้องของคำตอบ อีกเรื่องสำคัญคือข้อมูลและสิทธิ์การเข้าถึง



## 7. Security & Data Isolation — สิทธิ์และการแยกข้อมูล

เวลา 90 วินาที

### เนื้อหาบนสไลด์
ตรวจตัวตนและสิทธิ์ที่ Backend
ตรวจเจ้าของบอทก่อนเข้าถึงข้อมูล
ค้นความรู้จากดัชนีของบอทที่เลือก
LINE webhook ตรวจสอบ signature

### ภาพและตำแหน่ง
ด้านขวา: ภาพบอท A และ B กับความรู้แยกกัน
แสดงจุดตรวจสิทธิ์ก่อนเข้าถึงข้อมูล
ใต้ภาพ: เป็นการแยกเชิงตรรกะ
ไม่ใช่ฐานข้อมูลหรือเครื่องแยกต่อบอท

### บทพูด
การแยกข้อมูลในที่นี้เป็นการตรวจสิทธิ์และจำกัดการเข้าถึงตามเจ้าของและบอท รวมถึงการค้นในดัชนีของบอทที่เลือก ไม่ได้หมายความว่ามีฐานข้อมูลหรือเครื่องแยกต่อบอท และไม่ใช่การรับรองว่าผ่านการทดสอบเจาะระบบแล้ว การกำหนดสิทธิ์ การสำรองข้อมูล และการเก็บประวัติต้องปรับให้ตรงนโยบายองค์กร

ระบบจัดเก็บข้อมูลแยกตามหน้าที่ PostgreSQL ใช้เก็บข้อมูลที่มีความสัมพันธ์ชัดเจน เช่น ผู้ใช้เป็นเจ้าของบอท และบอทมีประวัติการสนทนา ส่วน ChromaDB เก็บข้อความย่อยกับ embeddings เพื่อใช้ค้นหา โดยมีการแยกความรู้ตามบอท และ Storage เก็บไฟล์เอกสารต้นฉบับ ในการเข้าใช้งานเว็บ ระบบใช้ token ยืนยันตัวตน แล้ว Backend ตรวจสิทธิ์ตามบทบาทและความเป็นเจ้าของบอทอีกครั้ง การมีเมนูบนหน้าจอจึงต้องสัมพันธ์กับสิทธิ์ที่ Backend บังคับใช้ด้วย สำหรับการนำไปใช้งานในบริษัท ทีมไอทีควรประเมินการกำหนดสิทธิ์จริง การสำรองข้อมูล และการจัดเก็บประวัติให้ตรงกับนโยบายองค์กร ซึ่งเป็นส่วนที่ต้องกำหนดตามสภาพแวดล้อมใช้งาน

ประโยคเชื่อม: ต่อไปคือกรณีที่การสนทนาต้องให้คนเข้ามาช่วย

[0:25–1:10] ต่อไปจะถามคำถามที่มีคำตอบอยู่ในเอกสาร ระหว่างรอ ระบบกำลังค้นข้อความที่เกี่ยวข้องและสร้างคำตอบ เมื่อคำตอบปรากฏให้ชี้ข้อมูลที่ตรงกับคำถาม แล้วเปิดชื่อไฟล์หรือข้อความประกอบบนเว็บเพื่อเทียบกับต้นฉบับ อธิบายเฉพาะผลที่เห็นบนหน้าจอ

[1:10–2:10] ต่อไปเป็นการขอคุยกับเจ้าหน้าที่ เปลี่ยนไปยังหน้าจอเจ้าของบอท แสดงการรับช่วงและตอบข้อความหนึ่งครั้ง แล้วกลับไปที่หน้าผู้สนทนาเพื่อดูข้อความตอบ จากนั้นจบ session

[2:10–2:30] การสาธิตนี้แสดงเส้นทางตั้งแต่ใช้เอกสารตอบคำถามจนถึงให้คนรับช่วง กรณีระบบช้าหรือบริการไม่พร้อม ให้เปิดวิดีโอจากการซ้อมที่เตรียมไว้ และบอกผู้ฟังว่าเป็นวิดีโอบันทึกการทำงาน

ประโยคเชื่อม: หลังเห็นการใช้งานแล้ว มาดูหลักฐานการทดสอบและสิ่งที่ยังต้องประเมิน



## 9. System Testing & Reliability — การทดสอบและความน่าเชื่อถือ

### เนื้อหาบนสไลด์
เอกสารรายงาน backend ผ่าน 139 กรณี

### ภาพและตำแหน่ง
ด้านขวา: ตารางกรณีทดสอบจากรายงานจริง
แยก regression tests กับการใช้โมเดลจริง
ระบุวันที่และชุดทดสอบ
ไม่ใช้ 139 กรณีเป็นค่าความแม่นยำ AI

### บทพูด
การประเมินระบบควรแยกความถูกต้องของโปรแกรมออกจากคุณภาพคำตอบของโมเดล เอกสารผลทดสอบในโครงการรายงานว่า backend ผ่าน 139 กรณี ณ การตรวจที่บันทึกไว้ โดยชุดทดสอบครอบคลุมงานข้อมูล สิทธิ์ และเงื่อนไขของกระบวนการ RAG ตัวอย่างกรณีคือการรักษาความหมายของคำปฏิเสธ การอ้างตัวเลขตามหลักฐาน การอ่านตารางจาก DOCX และคำถามต่อเนื่อง สำหรับ regression tests มีการจำลองผลตอบจากโมเดลเพื่อให้ทดสอบซ้ำได้ จึงยังใช้สรุปเป็นเปอร์เซ็นต์ความแม่นยำของโมเดลจริงไม่ได้

การประเมินกับผู้ใช้จริงควรเตรียมคำถามที่มีคำตอบอ้างอิง แยกคำถามที่มีข้อมูล ไม่มีข้อมูล และคำถามต่อเนื่อง แล้วตรวจทั้งความครบถ้วน ความถูกต้อง การอ้างอิง และเวลาตอบ โดยระบุเอกสาร รุ่นโมเดล และเครื่องที่ใช้ทุกครั้ง ผลส่วนนี้จะช่วยตอบได้ชัดว่าระบบเหมาะกับงานของบริษัทมากน้อยเพียงใด

ประโยคเชื่อม: ผลทดสอบเหล่านี้นำไปสู่ข้อจำกัดและลำดับการพัฒนาต่อ



## 10. Limitations & Future Work — ข้อจำกัดและการพัฒนาต่อ

เวลา 90 วินาที

### เนื้อหาบนสไลด์
คุณภาพเอกสารมีผลต่อการค้นคำตอบ
โมเดลและทรัพยากรเครื่องมีผลต่อเวลา
ทำ UAT และประเมินคำถามภาษาไทยจริง
ทดสอบโหลด สำรองข้อมูล และติดตามบริการ

### ภาพและตำแหน่ง
ด้านขวา: แผนพัฒนา 3 ระยะ
ประเมินคำตอบ → ทดลองใช้ → เตรียมใช้งาน
ติดป้ายว่าเป็นแผนงาน
ไม่ใส่ผล UAT ที่ยังไม่ได้ยืนยัน

### บทพูด
ข้อจำกัดแรกคือเอกสารต้นทาง หากข้อมูลไม่ครบ ล้าสมัย หรือโครงสร้างอ่านยาก ระบบอาจค้นหลักฐานได้ไม่ครบ จึงต้องมีผู้รับผิดชอบปรับปรุงความรู้ ข้อที่สองคือโมเดลและทรัพยากรเครื่องมีผลต่อคุณภาพกับเวลาตอบ โดยเฉพาะเมื่อมีผู้ใช้หลายคนพร้อมกัน จึงยังต้องวัดก่อนกำหนดขนาดเครื่องใช้งานจริง ข้อที่สามคือการตรวจคำตอบจากหลักฐานอาจทำให้บางคำถามถูกปฏิเสธ จึงต้องประเมินทั้งคำตอบผิดและกรณีที่ระบบปฏิเสธมากเกินไป

แนวทางพัฒนาต่อที่เสนอคือเริ่มจากชุดคำถามของหน่วยงานจริง แล้วให้ผู้ใช้ประเมินผ่าน UAT จากนั้นจึงปรับกระบวนการค้นหาและคำตอบ พร้อมวางแผนสำรองข้อมูล ติดตามสถานะบริการ และกำหนดผู้รับผิดชอบคิวแชท ก่อนขยายขอบเขตใช้งาน การทำตามลำดับนี้จะช่วยให้เห็นว่าจุดใดควรปรับจากหลักฐานการใช้งาน

ประโยคเชื่อม: ขอสรุปภาพรวมของ ScopeBot อีกครั้ง
