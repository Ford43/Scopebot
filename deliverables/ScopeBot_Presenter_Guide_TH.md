# ScopeBot — คู่มือพรีเซนต์และตรวจภาพ

## ใช้ไฟล์อย่างไร

เปิด PowerPoint แล้วดู Notes ใต้แต่ละสไลด์ มีบทพูด วิธีชี้ภาพ และประโยคส่งต่อ ไฟล์นี้สำรองบทพูดไว้ให้อ่านแยกจากสไลด์ เมื่อปรับใน Canva ควรเก็บคู่มือนี้ไว้ เพราะการนำเข้าอาจไม่รักษา Notes ทั้งหมด

ลำดับหลัก: ภาพรวม → Frontend และสิทธิ์ → Backend → Database → AI/RAG → ส่งต่อคน → Deployment → Timeline → Demo

ภาพ flow ส่วนใหญ่อ่านจากซ้ายไปขวาตามเลข ส่วน Sequence อ่านจากบนลงล่าง อย่าเริ่มจากชื่อเทคโนโลยีทั้งหมด ให้เริ่มว่าใครส่งอะไร และระบบทำอะไรต่อ

## สิ่งที่ตรวจพบใน PDF เดิมและแก้ในฉบับใหม่

- หน้า 1: เก็บธีมดำ ฟ้า ม่วง และรูปหุ่นยนต์เดิม ลดองค์ประกอบตกแต่งที่ไม่เกี่ยวกับระบบ
- หน้า 2: จัดสารบัญตามเส้นทางการเล่า ไม่แยกหัวข้อซ้ำ
- หน้า 3: ภาพที่เรียก Sequence เดิมเป็นภาพรวม ไม่ใช่ลำดับเวลา แทนด้วย sequence คำถามหนึ่งครั้งในสไลด์ 12
- หน้า 4: แผนภาพภาพรวมเดิมรวมรายละเอียดหลายระดับ และเส้นเชื่อมชวนเข้าใจผิด แยกภาพรวมในสไลด์ 4 กับ Deployment ในสไลด์ 14 ใช้ Cloudflare Tunnel จุดเดียว และให้ ChromaDB เชื่อมกับขั้นค้นหา
- หน้า 5–6: ลดรายละเอียด Frontend เหลือเส้นทางเข้าใช้งาน และแยกสิทธิ์เป็นสไลด์ 6 แก้ Support ให้ตรงโค้ด: ดูแลบัญชี ไม่ใช่ผู้ตอบ Live Chat; เจ้าของบอทเป็นผู้รับช่วงแชท
- หน้า 7: แก้ประเภทเทคโนโลยี Python เป็นภาษา FastAPI เป็น framework และ JWT ใช้ยืนยันตัวตน
- หน้า 8: ภาพ Backend เดิมซ้ำกับ Frontend เปลี่ยนเป็นขั้นรับคำขอ ตรวจสิทธิ์ เลือกงาน และประมวลผล
- หน้า 9: แทนข้อความฐานข้อมูลที่ยังไม่สมบูรณ์ด้วยหน้าที่ของ PostgreSQL, ChromaDB, Storage และความสัมพันธ์จริงจาก models
- หน้า 10: ตัดไอคอนที่ไม่เกี่ยวข้อง แยก RAG เป็นการเตรียมความรู้และการตอบคำถาม ไม่อธิบายว่าเป็นการฝึกโมเดลใหม่
- หน้า 11: ใช้ภาพ handoff และ Deployment แบบย่อประกอบรายละเอียดของระบบ แทนการอัดทุกเส้นทางลงภาพเดียว
- หน้า 12: รักษาแผน มี.ค.–ต.ค. 2569 แต่ไม่อ้างว่า UAT ผ่านแล้ว ช่วง ก.ย.–ต.ค. ระบุเป็นแผน ต้องยืนยันผลจริงก่อนรายงาน
- หน้า 13: เพิ่มขั้นตอน Demo ที่เดินตามได้ และข้อเตรียมพร้อม แทนหัวข้อ Demo อย่างเดียว
- หน้า 14–18: รวมภาพและชื่อสมาชิกเป็นหน้าเดียว เพื่อให้เวลาไปอยู่ที่เนื้อหาระบบ ช่วงรับผิดชอบในบทพูดเป็นข้อเสนอสำหรับซ้อม ไม่ใช่การยืนยันหน้าที่ของสมาชิก

ภาพทางเทคนิคเดิมบางส่วนมีข้อมูลผิด ไม่ใช่เพียงวาดซับซ้อน ฉบับนี้อ้างอิงโค้ดใน repository แต่การตรวจโค้ดไม่ใช่การทดสอบระบบสด จึงยังต้องซ้อม Demo และตรวจบริการก่อนวันนำเสนอ

## Checklist ก่อนนำเสนอ

- ยืนยันวันและสถานะ Timeline รวมถึงผล UAT กับทีม
- ตรวจชื่อสมาชิกและตกลงคนพูดแต่ละช่วง
- ใช้บัญชีเจ้าของบอทที่ได้รับอนุมัติ บอท active และประมวลผลเอกสารแล้ว
- เปิด API, PostgreSQL, Ollama และช่องทาง LINE ที่จะสาธิต ตรวจว่าตอบจริง
- เตรียมเอกสารที่ไม่มีข้อมูลส่วนบุคคล และคำถามที่มีคำตอบในเอกสาร
- ซ้อมการส่งต่อคน ตอบในแชทรวม และจบ session
- เตรียมภาพหรือวิดีโอสำรองจากการซ้อมจริง หากบริการไม่พร้อม ไม่อ้างผลที่ยังไม่เกิด

### 6. บทบาทและขอบเขตข้อมูล

### 7. Backend

เวลา 60 วินาที
ชี้เลข 1 Backend รับคำขอจาก Web หรือ webhook ของ LINE
เลข 2 คำขอ Web ตรวจ JWT บัญชีและสิทธิ์ ส่วน LINE ตรวจ signature
เลข 3 Router เรียกงาน เช่น จัดการบอท เอกสาร หรือแชท
เลข 4 อ่านเขียนข้อมูล เรียก RAG แล้วส่งผลกลับ
ไม่ต้องอ่านทุก endpoint ในช่วงนี้ รายชื่ออยู่ภาคผนวก
ส่งต่อ: ระบบเก็บข้อมูลสามชนิดในคนละส่วน

อ้างอิง: api/main.py; api/auth.py; api/routers/*.py

### 8. ข้อมูลอยู่ที่ไหน

เวลา 60 วินาที
อธิบายจากซ้ายไปขวา PostgreSQL เก็บผู้ใช้ บอท metadata เอกสารและประวัติ ผ่าน SQLAlchemy
ChromaDB เก็บข้อความย่อยกับ embeddings โดยแยก directory ตาม bot_id ไม่ใช่ PostgreSQL คนละฐานต่อบอท

ส่งต่อ: ดูเฉพาะความสัมพันธ์ฐานข้อมูลที่เกี่ยวกับบอทก่อน

อ้างอิง: api/database.py; api/models.py; rag/ingest.py; docker-compose.yml

### 9. Database Relationships

เวลา 70 วินาที
ชี้ users เป็นเจ้าของ bots และ documents ได้หลายรายการ
บอทกับเอกสารเชื่อมผ่าน bot_documents จึงให้เอกสารเดียวใช้กับหลายบอทได้
บอทหนึ่งมี conversations หลายรายการ และ live_sessions หลายครั้ง แต่ละ live_session มี live_messages หลายข้อความ
นี่เป็น ER ย่อ ตาราง notifications password_reset_tokens audit_logs อยู่ในฐานเดียวกันแต่ไม่ใส่ในภาพหลักเพื่อให้อ่านง่าย
ส่งต่อ: เมื่อบอทมีเอกสารแล้ว ระบบจะสร้างฐานความรู้ให้บอท

อ้างอิง: api/models.py

### 10. RAG ขั้นที่ 1 เตรียมความรู้

เวลา 60 วินาที
อ่าน 1 ถึง 4 ผู้ใช้ส่งเอกสาร ระบบอ่านและแบ่งข้อความ BGE-M3 แปลงข้อความย่อยเป็น embeddings แล้ว ChromaDB เก็บไว้แยกตามบอท
ขั้นนี้เป็นการเตรียมดัชนีความรู้ ไม่ใช่ฝึกโมเดลภาษาใหม่ และยังไม่ใช่ขั้นตอบคำถาม
ส่งต่อ: เมื่อผู้ใช้ถาม ระบบใช้ดัชนีนี้อย่างไร

อ้างอิง: rag/ingest.py; rag/document_loader.py; rag/chunker.py; api/routers/documents.py

### 11. RAG ขั้นที่ 2 ตอบคำถาม

เวลา 75 วินาที
ชี้ 1 คำถามใหม่และบริบทคำถามล่าสุดช่วยให้เข้าใจคำถามต่อเนื่อง
ชี้ 2 ตัว embedding แปลงคำค้นเพื่อหา chunks ที่ใกล้เคียงใน ChromaDB และกรองตาม distance
ชี้ 3 เอาข้อความที่ค้นได้เป็น context ส่งให้ Ollama พร้อมคำสั่งและประวัติ
ชี้ 4 คืนคำตอบพร้อมชื่อไฟล์และ snippet ให้ Web ส่วน LINE ส่งเป็นข้อความตาม router
ChromaDB เชื่อมที่การค้นหา ไม่ได้เป็นเส้นลัดเข้าโมเดล
ส่งต่อ: ดูคำถามเดียวกันในลำดับเวลาตั้งแต่ส่งจนตอบ

อ้างอิง: rag/rag_pipeline.py; rag/retriever.py; src/app/hooks/useChatSession.ts; api/routers/line_webhook.py

### 12. Sequence ของคำถามหนึ่งครั้ง

เวลา 60 วินาที
ชี้หัวคอลัมน์ Web FastAPI และ RAG ก่อน แล้วอ่านจากบนลงล่าง
1 Web ส่งคำถามและ session 2 FastAPI เรียก RAG หลังตรวจสิทธิ์ 3 RAG คืนคำตอบจากเอกสาร 4 Backend บันทึก conversation 5 ส่งคำตอบกลับ Web
หน้านี้เป็น sequence แบบย่อ รายละเอียดค้นหาและ LLM อยู่หน้าก่อน
ส่งต่อ: อีกเส้นทางหนึ่งเกิดเมื่อบอทตอบไม่ได้

อ้างอิง: api/routers/chat.py; rag/rag_pipeline.py

### 13. เมื่อบอทตอบไม่ได้

เวลา 60 วินาที
อ่านตามเลข 1 ถึง 4 bot ตอบจากเอกสาร เมื่อเข้า handoff จะรอใน waiting พอคนตอบครั้งแรกจึงเปลี่ยนเป็น human หลังจบงานกลับ bot และปิด active session
Web ที่ไม่พบคำตอบแสดงปุ่มให้เลือกติดต่อเจ้าหน้าที่ ส่วน LINE สามารถเข้าสู่คิวอัตโนมัติ
คนตอบคือเจ้าของบอทหรือ Admin ที่เป็นเจ้าของ ไม่ใช่ role Support ของแพลตฟอร์ม
ส่งต่อ: ทั้งสองช่องทางเชื่อมผ่าน deployment เดียวกัน

อ้างอิง: api/routers/chat.py; api/routers/live_chat.py; api/routers/line_webhook.py; api/auth.py

### 14. Deployment

เวลา 60 วินาที
อ่านซ้ายไปขวา Browser และ LINE ส่ง HTTPS เข้า Tunnel จากนั้นไป Nginx
Nginx ให้ไฟล์ React กับ browser ส่วนเส้นทาง /api/ ส่งไป FastAPI รวม webhook
FastAPI ติดต่อ PostgreSQL และ volume เอกสารกับ ChromaDB ภายใน deployment ส่วน Ollama รันบน host ตาม compose
ส่งต่อ: ต่อไปคือแผนดำเนินงานและส่วนที่ใช้ Demo

อ้างอิง: docker-compose.yml; docker-compose.tunnel.yml; deploy/nginx.conf

### 18. ภาคผนวก API หลัก

ไม่จำเป็นต้องอ่านหน้านี้ในช่วงหลัก
อธิบายเฉพาะกลุ่มที่ผู้ฟังถาม เช่น /api/auth สำหรับบัญชี /api/bots และ /api/documents สำหรับความรู้ /api/chat สำหรับคำถามและประวัติ /api/live สำหรับรับช่วงแชท
