# บทที่ 3
# การวิเคราะห์และการออกแบบระบบ

โครงงานภาคอุตสาหกรรมแชตบอตอัจฉริยะสำหรับสนับสนุนการให้บริการลูกค้าจากข้อมูลในเอกสาร บริษัท โทรคมนาคมแห่งชาติ จำกัด (มหาชน) (NT) เป็นการพัฒนาระบบ Scopebot เพื่อใช้เอกสารเป็นฐานความรู้สำหรับตอบคำถาม รองรับการรับส่งข้อความผ่านเว็บไซต์และ LINE Official Account (LINE OA) และรวบรวมข้อมูลการสนทนาไว้ในระบบเดียวสำหรับตรวจสอบย้อนหลัง

การวิเคราะห์และออกแบบระบบในบทนี้ประกอบด้วยขอบเขตการทำงาน แผนภาพยูสเคส คำอธิบายยูสเคส แผนภาพกิจกรรม การออกแบบฐานข้อมูล พจนานุกรมข้อมูล และการออกแบบส่วนติดต่อผู้ใช้ โดยกำหนดการเข้าถึงข้อมูลตามบทบาทและความเป็นเจ้าของบอท เพื่อให้การจัดการเอกสารและบทสนทนาอยู่ภายในขอบเขตสิทธิ์ของผู้ใช้งาน

## 3.1 ขอบเขตการทำงานของระบบ

### 3.1.1 ภาพรวมของระบบ

ระบบแบ่งการทำงานเป็นส่วนติดต่อผู้ใช้ผ่านเว็บไซต์ ส่วนให้บริการข้อมูล และส่วนค้นหาและสร้างคำตอบจากเอกสาร เว็บไซต์พัฒนาด้วย React และ TypeScript โดยใช้ Vite และ Tailwind CSS ส่วนให้บริการข้อมูลพัฒนาด้วย FastAPI และจัดการข้อมูลเชิงสัมพันธ์ผ่าน SQLAlchemy ส่วนตอบคำถามใช้แนวทาง Retrieval-Augmented Generation (RAG) ร่วมกับแบบจำลองภาษาที่เรียกผ่าน Ollama และฐานข้อมูลเวกเตอร์ Chroma หรือ Qdrant ตามการตั้งค่าของบอท

กระบวนการเตรียมความรู้เริ่มจากการนำเข้าเอกสาร อ่านข้อความ แบ่งข้อความเป็นส่วนย่อย และสร้างเวกเตอร์ เมื่อผู้ใช้ส่งคำถาม ระบบค้นหาข้อความในฐานความรู้ของบอทนั้นและใช้หลักฐานประกอบคำตอบ พร้อมตรวจสอบความสอดคล้องของคำตอบกับข้อมูลที่ค้นพบ หากหลักฐานไม่เพียงพอ ระบบแจ้งข้อจำกัดและเสนอช่องทางติดต่อผู้ดำเนินงานตามเงื่อนไขของช่องทางสนทนา

### 3.1.2 ผู้สมัครและผู้ใช้งานบัญชีทั่วไป

ผู้สมัครสามารถสร้างบัญชีใหม่โดยกรอกอีเมล ชื่อผู้ใช้ และรหัสผ่าน บัญชีใหม่ต้องรอการอนุมัติก่อนเข้าใช้งาน เมื่อได้รับอนุมัติแล้ว ผู้ใช้บทบาท User สามารถจัดการบอทและข้อมูลของตนเองภายในจำนวนบอทที่ได้รับอนุญาต ในโครงงานนี้ใช้คำว่า “ผู้ดูแลบอท” เพื่ออธิบายหน้าที่ของบัญชีที่จัดการบอท โดยไม่ได้หมายถึงบทบาท Admin เสมอไป

1. สมัครสมาชิก — ข้อมูลเข้า ได้แก่ อีเมล ชื่อผู้ใช้ และรหัสผ่าน ผลลัพธ์คือบัญชีใหม่ที่มีสถานะรออนุมัติ
2. เข้าสู่ระบบ — ข้อมูลเข้า ได้แก่ อีเมลและรหัสผ่าน ผลลัพธ์คือสิทธิ์เข้าใช้งานตามสถานะและบทบาทบัญชี
3. จัดการบอท — ข้อมูลเข้า ได้แก่ ชื่อ คำอธิบาย และฐานค้นหาของบอท ผลลัพธ์คือรายการบอทภายใต้บัญชีของตนเอง
4. จัดการเอกสารความรู้ — ข้อมูลเข้า ได้แก่ไฟล์ PDF, DOCX, TXT หรือ CSV และบอทเป้าหมาย ผลลัพธ์คือเอกสารในคลังและฐานความรู้ที่พร้อมเมื่อประมวลผลสำเร็จ
5. สนทนาบนเว็บไซต์ — ข้อมูลเข้า ได้แก่ บอทที่เลือก คำถาม และรอบสนทนา ผลลัพธ์คือคำตอบหรือข้อความแจ้งสถานะ พร้อมประวัติที่เกี่ยวข้อง
6. เชื่อมต่อ LINE OA — ข้อมูลเข้า ได้แก่บอทและข้อมูลช่องทาง LINE ผลลัพธ์คือการตั้งค่าช่องทางสำหรับรับส่งข้อความ
7. รับช่วงสนทนา — ข้อมูลเข้า ได้แก่รอบสนทนาที่รอผู้ดำเนินงานและข้อความตอบกลับ ผลลัพธ์คือข้อความที่บันทึกและการส่งต่อไปยังช่องทางที่เกี่ยวข้อง
8. ตรวจสอบประวัติและภาพรวม — ข้อมูลเข้า ได้แก่บอท รายการสนทนา หรือช่วงเวลาที่เลือก ผลลัพธ์คือประวัติและข้อมูลสรุปภายในขอบเขตสิทธิ์

หน้าสนทนาบนเว็บไซต์ในรุ่นที่ตรวจสอบเป็นหน้าที่ต้องเข้าสู่ระบบและตรวจสิทธิ์ความเป็นเจ้าของบอท จึงไม่ได้กำหนดให้ลูกค้าทั่วไปที่ไม่มีบัญชีเข้าถึงบอทขององค์กรทุกตัวได้ ส่วนผู้สนทนาผ่าน LINE ใช้ตัวระบุผู้ใช้จาก LINE และไม่จำเป็นต้องมีบัญชีในตารางผู้ใช้ของ Scopebot

### 3.1.3 ผู้ดูแลระบบ Admin และผู้สนับสนุนระบบ Support

Admin และ Support สามารถเข้าถึงส่วนจัดการผู้ใช้งานตามสิทธิ์ที่กำหนด เช่น การพิจารณาบัญชีรออนุมัติ โดย Support ไม่สามารถแก้ไขบัญชี Admin และการเปลี่ยนบทบาทสงวนให้ Admin การจัดการบอท เอกสาร และบทสนทนาของผู้ดูแลบอทแยกจากหน้าที่จัดการผู้ใช้ของแพลตฟอร์ม

1. พิจารณาบัญชีผู้ใช้ — ข้อมูลเข้า ได้แก่บัญชีเป้าหมายและผลการพิจารณา ผลลัพธ์คือสถานะบัญชีที่ปรับปรุงตามสิทธิ์
2. จัดการสถานะและสิทธิ์ — ข้อมูลเข้า ได้แก่สถานะการใช้งาน จำนวนบอทที่อนุญาต หรือบทบาทตามสิทธิ์ผู้ดำเนินการ ผลลัพธ์คือข้อกำหนดบัญชีที่เปลี่ยนแปลงและบันทึกการดำเนินการ
3. ตรวจสอบการบริหารระบบ — Admin ใช้ข้อมูลภาพรวมระบบและบันทึกการดำเนินการประกอบการดูแลแพลตฟอร์ม ขณะที่ข้อมูลบอทและบทสนทนายังคงมีการตรวจสิทธิ์ความเป็นเจ้าของ

คำว่า “ผู้ดำเนินงาน” ในการรับช่วงสนทนาหมายถึงบัญชีที่มีสิทธิ์ดูแลบอทนั้น ไม่ใช่การกำหนดให้บัญชี Support ตอบบทสนทนาของทุกบอทได้

### 3.1.4 ผู้สนทนาผ่าน LINE OA

ผู้สนทนาสามารถส่งคำถามผ่าน LINE OA ที่เชื่อมกับบอท รับข้อความตอบกลับ และร้องขอติดต่อผู้ดำเนินงานได้ ระบบใช้ข้อมูลเหตุการณ์จาก LINE เพื่อระบุบอทและรอบสนทนา โดยบันทึกข้อความสำหรับการตรวจสอบในระบบกลาง ทั้งนี้ การรวบรวมข้อมูลสองช่องทางไม่ได้หมายถึงการรวมตัวตนผู้ใช้เว็บไซต์กับ LINE เป็นบุคคลเดียวกันโดยอัตโนมัติ

### 3.1.5 ขอบเขตและเงื่อนไขของข้อมูล

เอกสารความรู้ต้องได้รับอนุญาตให้นำมาใช้งานและมีเนื้อหาที่อ่านได้ การตอบคำถามต้องอาศัยหลักฐานจากเอกสารของบอทที่เกี่ยวข้อง และไม่ใช้คำตอบเดิมของบอทเป็นข้อเท็จจริง การแสดงเลขหน้าอ้างอิงทำได้เมื่อข้อมูลแหล่งอ้างอิงมีเลขหน้า การปรับปรุงเอกสารใช้การสร้างฐานความรู้รุ่นใหม่ก่อนเผยแพร่ โดยการลบหรือแทนที่ข้อมูลมีเงื่อนไขป้องกันการตอบจากความรู้ที่ถูกถอนออก

## 3.2 แผนภาพยูสเคส (Use Case Diagram)

การออกแบบกำหนดขอบเขตระบบเป็น “Scopebot” และแสดงกิจกรรมที่ผู้ใช้งานภายนอกโต้ตอบกับระบบ โดยแบ่ง Actor ตามหน้าที่ ได้แก่ ผู้สมัคร ผู้ดูแลบอท ผู้ดูแลระบบ Admin ผู้สนับสนุนระบบ Support และผู้สนทนาผ่าน LINE OA ส่วน LINE Platform เป็นระบบภายนอกที่รับส่งเหตุการณ์ข้อความกับ Scopebot ผู้ดำเนินงานรับช่วงสนทนาเป็นหน้าที่ของผู้ดูแลบอทที่มีสิทธิ์เข้าถึงบอทนั้น

กำหนดยูสเคสหลัก 11 รายการดังนี้

1. UC01 สมัครสมาชิก — ผู้สมัคร
2. UC02 เข้าสู่ระบบ — ผู้ดูแลบอท, Admin และ Support
3. UC03 พิจารณาอนุมัติผู้ใช้งาน — Admin และ Support ภายในสิทธิ์
4. UC04 จัดการบอท — ผู้ดูแลบอท
5. UC05 จัดการเอกสารและฐานความรู้ — ผู้ดูแลบอท
6. UC06 ตั้งค่าการเชื่อมต่อ LINE OA — ผู้ดูแลบอท
7. UC07 สนทนาผ่านเว็บไซต์ — ผู้ดูแลบอทหรือผู้ใช้เว็บไซต์ที่มีสิทธิ์ในบอท
8. UC08 สนทนาผ่าน LINE OA — ผู้สนทนาผ่าน LINE OA และ LINE Platform
9. UC09 รับช่วงสนทนาโดยผู้ดำเนินงาน — ผู้ดูแลบอท และผู้สนทนาที่ขอความช่วยเหลือ
10. UC10 ตรวจสอบประวัติการสนทนา — ผู้ดูแลบอท
11. UC11 ดูข้อมูลสรุปการใช้งาน — ผู้ดูแลบอท

## 3.3 คำอธิบายยูสเคส (Use Case Description)

คำอธิบายแต่ละยูสเคสประกอบด้วยผู้กระทำหลัก ผู้เกี่ยวข้อง วัตถุประสงค์ เงื่อนไขก่อนและหลังการทำงาน ลำดับหลัก และทางเลือกเมื่อเกิดเงื่อนไขแตกต่าง เพื่อใช้เป็นข้อมูลสำหรับออกแบบกิจกรรมและตรวจสอบความสอดคล้องของระบบ

### 3.3.1 สมัครสมาชิก

ตารางที่ 3.1 คำอธิบายยูสเคสสมัครสมาชิก

| รายการ | รายละเอียด |
| --- | --- |
| Use Case Name | UC01 สมัครสมาชิก |
| Primary Actor | ผู้สมัคร |
| Related Actor | Admin และ Support ในฐานะผู้รับการแจ้งเตือน |
| Description | สร้างบัญชีใหม่เพื่อรอการอนุมัติเข้าใช้งาน |
| Pre-condition | ผู้สมัครเข้าถึงหน้าสมัครสมาชิกได้ |
| Post-condition | มีบัญชี User ที่ยังไม่ได้รับอนุมัติ พร้อมการแจ้งเตือนและบันทึก signup |
| Main Flow | 1. ผู้สมัครกรอกอีเมล ชื่อผู้ใช้ และรหัสผ่าน แล้วส่งแบบฟอร์ม<br>2. ระบบตรวจความซ้ำของอีเมลและชื่อผู้ใช้ และตรวจความยาวรหัสผ่านอย่างน้อย 6 ตัวอักษร<br>3. ระบบแฮชรหัสผ่านด้วย bcrypt และบันทึกบัญชี role=user, is_approved=false และ is_active=true ตามค่าเริ่มต้น<br>4. ระบบสร้างการแจ้งเตือนให้บัญชี Admin และ Support<br>5. ระบบบันทึก audit log ชนิด signup<br>6. เว็บไซต์แสดงข้อความสมัครสำเร็จและรออนุมัติ |
| Alternative Flow | A1 อีเมลหรือชื่อผู้ใช้ซ้ำ: แจ้งข้อผิดพลาดและไม่สร้างบัญชี<br>A2 รหัสผ่านสั้นกว่า 6 ตัวอักษร: แจ้งข้อผิดพลาดและไม่สร้างบัญชี<br>A3 ข้อมูลไม่ตรงรูปแบบคำขอ: แจ้งข้อผิดพลาดให้แก้ไข |
| Special Requirements | ไม่เก็บรหัสผ่านเป็นข้อความธรรมดา และไม่ให้บัญชีรออนุมัติเข้าสู่ระบบ |

### 3.3.2 เข้าสู่ระบบ

ตารางที่ 3.2 คำอธิบายยูสเคสเข้าสู่ระบบ

| รายการ | รายละเอียด |
| --- | --- |
| Use Case Name | UC02 เข้าสู่ระบบ |
| Primary Actor | ผู้ใช้ที่มีบัญชี รวมถึง User, Admin และ Support |
| Related Actor | ไม่มี |

## 3.4 แผนภาพกิจกรรม (Activity Diagram)

แผนภาพกิจกรรมแสดงลำดับการทำงานตามยูสเคส โดยแบ่งช่องผู้รับผิดชอบระหว่างผู้ใช้งาน ระบบ Scopebot และระบบภายนอกเมื่อเกี่ยวข้อง ใช้กิจกรรมสำหรับขั้นตอนการกระทำ จุดตัดสินใจสำหรับเงื่อนไข และจุดรวมทางเลือกเมื่อเส้นทางกลับมาดำเนินการร่วมกัน จำนวนกิจกรรมอาจแตกต่างจากจำนวนข้อใน Main Flow แต่ต้องรักษาลำดับ เงื่อนไข และผลลัพธ์ที่กำหนดไว้

### 3.4.1 กิจกรรมสมัครสมาชิก

ผู้สมัครกรอกข้อมูลและส่งคำขอ ระบบตรวจข้อมูล หากไม่ผ่านจะแสดงสาเหตุและให้กลับไปแก้ไข หากผ่านจะบันทึกบัญชีรออนุมัติ สร้างการแจ้งเตือน บันทึก audit log และแสดงข้อความสมัครสำเร็จ กระบวนการนี้สิ้นสุดก่อนการพิจารณาอนุมัติ

[แทรกภาพที่ 3.2: Activity UC01 แบ่งช่องผู้สมัคร/ระบบ ลำดับ เปิดแบบฟอร์ม → กรอกและส่ง → ตรวจข้อมูล → ตัดสินใจผ่านหรือไม่ ทางไม่ผ่านแสดงข้อผิดพลาดและย้อนผ่านจุดรวมก่อนกรอก ทางผ่านแฮชรหัสผ่านและบันทึกบัญชี → แจ้งเตือน → audit log → แสดงผล → สิ้นสุด]

ภาพที่ 3.2 แผนภาพกิจกรรมสมัครสมาชิก

### 3.4.2 กิจกรรมเข้าสู่ระบบ

ระบบตรวจอีเมลและรหัสผ่านก่อนตรวจสถานะการใช้งานและการอนุมัติ โดยแยกผลข้อมูลไม่ถูกต้อง บัญชีถูกระงับ และยังไม่ได้รับอนุมัติออกจากทางเข้าสู่ระบบสำเร็จ

[แทรกภาพที่ 3.3: Activity UC02 ช่องผู้ใช้/ระบบ กรอกข้อมูล → ตรวจรหัสผ่าน → ถูกต้องหรือไม่ → ตรวจ active → ตรวจ approved → ออก token → แสดงหน้าตามบทบาท ทางข้อมูลผิดย้อนกรอก ทางถูกระงับหรือรออนุมัติแจ้งสาเหตุแล้วจบ]

ภาพที่ 3.3 แผนภาพกิจกรรมเข้าสู่ระบบ

### 3.4.3 กิจกรรมพิจารณาอนุมัติผู้ใช้งาน

ผู้ดำเนินการเลือกบัญชีจากรายการที่มีสิทธิ์และพิจารณาข้อมูล ระบบตรวจสิทธิ์ก่อนปรับสถานะ เมื่อมีการเปลี่ยนสถานะจะบันทึกการดำเนินการ การไม่อนุมัติคงข้อจำกัดการเข้าสู่ระบบและไม่เท่ากับการลบบัญชี

[แทรกภาพที่ 3.4: Activity UC03 ช่อง Admin หรือ Support/ระบบ เปิดรายการ → เลือกบัญชี → ตรวจสิทธิ์ → พิจารณา → อนุมัติหรือไม่ → กำหนดสถานะตามผล → รวมทางเลือก → บันทึกการเปลี่ยนแปลงเมื่อมี → แสดงผล → จบ ทางไม่มีสิทธิ์แจ้งข้อผิดพลาด]

ภาพที่ 3.4 แผนภาพกิจกรรมพิจารณาอนุมัติผู้ใช้งาน

### 3.4.4 กิจกรรมจัดการบอท

ผู้ดูแลบอทเลือกสร้าง แก้ไข หรือลบบอท ระบบตรวจข้อมูลและสิทธิ์ตามการกระทำ โดยการสร้างตรวจจำนวนบอทที่อนุญาต ส่วนการแก้ไขและลบตรวจความเป็นเจ้าของบอทก่อนดำเนินการ

[แทรกภาพที่ 3.5: Activity UC04 ช่องผู้ดูแลบอท/ระบบ เปิดรายการ → เลือกการทำงาน แยกสามทาง สร้าง: กรอกข้อมูลและตรวจโควตา แก้ไข: เลือกบอทและตรวจสิทธิ์ ลบ: เลือกบอท ตรวจสิทธิ์ และยืนยัน → ดำเนินการตามทาง → รวมทางเลือก → แสดงรายการล่าสุด → จบ แยกทางยกเลิกและข้อมูลไม่ผ่าน]

ภาพที่ 3.5 แผนภาพกิจกรรมจัดการบอท

### 3.4.5 กิจกรรมจัดการเอกสารและฐานความรู้

ระบบตรวจไฟล์และบอทเป้าหมายก่อนกำหนดเอกสาร จากนั้นสร้างฐานความรู้รุ่นใหม่และเผยแพร่เมื่อสำเร็จ หากเกิดข้อผิดพลาด ระบบแสดงสาเหตุและคงเงื่อนไขความพร้อมตามประเภทการปรับปรุง

[แทรกภาพที่ 3.6: Activity UC05 ช่องผู้ดูแลบอท/ระบบ เลือกอัปโหลดหรือเอกสารเดิม → ตรวจสิทธิ์และข้อมูล → ชื่อซ้ำหรือไม่ → ยืนยันแทนที่เมื่อจำเป็น → กำหนดเอกสาร → จัดคิว → อ่านและแบ่งข้อความ → สร้างเวกเตอร์ → ตรวจผลและรุ่น → สำเร็จหรือไม่ ทางสำเร็จเผยแพร่ ทางผิดพลาดแสดงสาเหตุและทางเลือกลองใหม่ การลบแสดงเป็นทางปรับเอกสารก่อนจัดคิว]

ภาพที่ 3.6 แผนภาพกิจกรรมจัดการเอกสารและฐานความรู้

### 3.4.6 กิจกรรมตั้งค่าการเชื่อมต่อ LINE OA

การตั้งค่าประกอบด้วยส่วนที่ดำเนินการใน Scopebot และส่วนที่ดำเนินการบน LINE Platform จึงต้องแสดงระบบภายนอกให้ชัดเจน และใช้ผลรับส่งข้อความทดสอบประกอบการตรวจความพร้อม

[แทรกภาพที่ 3.7: Activity UC06 ช่องผู้ดูแลบอท/Scopebot/LINE Platform เลือกบอท → กรอกค่าช่องทาง → ตรวจสิทธิ์และบันทึก → ตั้ง webhook ใน LINE → เปิดเชื่อมต่อ → ส่งข้อความทดสอบ → รับส่งสำเร็จหรือไม่ ทางไม่สำเร็จตรวจและแก้การตั้งค่า ทางสำเร็จจบ]

ภาพที่ 3.7 แผนภาพกิจกรรมตั้งค่าการเชื่อมต่อ LINE OA

### 3.4.7 กิจกรรมสนทนาผ่านเว็บไซต์

ระบบตรวจสิทธิ์และความพร้อมก่อนประมวลผลคำถาม โดยแยกกรณีคำถามทั่วไปที่เข้าสู่ RAG ออกจากคำขอติดต่อผู้ดำเนินงานและรอบที่อยู่ในโหมดรับช่วงสนทนา ผล RAG มีทั้งคำตอบที่ผ่านการตรวจ กรณีหลักฐานไม่เพียงพอ และข้อผิดพลาดของบริการ

[แทรกภาพที่ 3.8: Activity UC07 ช่องผู้ใช้เว็บไซต์/ระบบ เลือกบอทและส่ง → ตรวจสิทธิ์และความพร้อม → ตรวจข้อความ → ตรวจโหมดหรือคำขอผู้ดำเนินงาน แยกทางไป UC09 กับทาง RAG → ค้นหลักฐาน → สร้างและตรวจคำตอบ → แยกตอบได้/ข้อมูลไม่พอ/บริการผิดพลาด → บันทึกสถานะ → แสดงผล → จบ]

ภาพที่ 3.8 แผนภาพกิจกรรมสนทนาผ่านเว็บไซต์

### 3.4.8 กิจกรรมสนทนาผ่าน LINE OA

LINE Platform ส่งเหตุการณ์ให้ระบบตรวจลายเซ็นก่อนประมวลผล ระบบบันทึกข้อความผู้ใช้และตรวจโหมดสนทนา คำทักทายอาจใช้ข้อความตอบทั่วไป ส่วนคำถามจากเอกสารเข้าสู่ RAG เมื่อฐานความรู้พร้อม

[แทรกภาพที่ 3.9: Activity UC08 ช่องผู้สนทนา/LINE Platform/Scopebot ส่งข้อความ → webhook → ตรวจบอทและลายเซ็น → ตรวจชนิดเหตุการณ์ → ระบุรอบและบันทึกข้อความ → ตรวจโหมดและคำขอติดต่อ → แยกคำทักทายหรือคำถาม RAG → สร้างผลตอบ → ส่งผ่าน LINE → บันทึกข้อมูลตามเส้นทาง → จบ เพิ่มทางข้ามเหตุการณ์ที่ไม่รองรับและทางผิดพลาด]

ภาพที่ 3.9 แผนภาพกิจกรรมสนทนาผ่าน LINE OA

### 3.4.9 กิจกรรมรับช่วงสนทนาโดยผู้ดำเนินงาน

เมื่อผู้ใช้ร้องขอ ระบบเปลี่ยนรอบเป็นสถานะรอ ผู้ดำเนินงานเลือกเรื่องและเริ่มตอบ ทำให้สถานะเป็น human ข้อความถูกบันทึกตามผู้ส่งจนผู้ดำเนินงานเลือกจบการสนทนา

[แทรกภาพที่ 3.10: Activity UC09 ช่องผู้สนทนา/ระบบ/ผู้ดำเนินงาน ขอความช่วยเหลือ → สถานะ waiting → เปิดเรื่องและตรวจสิทธิ์ → ส่งคำตอบแรก → สถานะ human → บันทึกและส่งข้อความ → สนทนาต่อหรือจบ ทางต่อวนผ่านจุดรวม ทางจบปิด live session บันทึกเวลาและกลับโหมดบอท]

ภาพที่ 3.10 แผนภาพกิจกรรมรับช่วงสนทนาโดยผู้ดำเนินงาน

### 3.4.10 กิจกรรมตรวจสอบประวัติการสนทนา

ผู้ดูแลบอทเปิดรายการประวัติและเลือกข้อมูลที่ต้องการ ระบบแสดงรายละเอียดจากข้อมูลภายในขอบเขตสิทธิ์ หากไม่พบรายการให้แสดงสถานะไม่มีข้อมูลและเปิดให้เปลี่ยนเงื่อนไข

[แทรกภาพที่ 3.11: Activity UC10 ช่องผู้ดูแลบอท/ระบบ เปิดประวัติ → ตรวจสิทธิ์และดึงรายการ → เลือกบอทหรือค้นหา → พบรายการหรือไม่ → เลือกรอบ → แสดงข้อความและช่องทาง → จบ ทางไม่พบแสดงสถานะและให้เปลี่ยนเงื่อนไข]

ภาพที่ 3.11 แผนภาพกิจกรรมตรวจสอบประวัติการสนทนา

### 3.4.11 กิจกรรมดูข้อมูลสรุปการใช้งาน

ระบบรวบรวมข้อมูลในขอบเขตที่ผู้ใช้มีสิทธิ์และแสดงตามช่วงเวลาที่เลือก โดยต้องแยกจำนวนรายการสนทนา จำนวนรอบ และคิวรอ เพื่อไม่ให้ผู้ใช้ตีความหน่วยนับคลาดเคลื่อน

[แทรกภาพที่ 3.12: Activity UC11 ช่องผู้ดูแลบอท/ระบบ เปิดแดชบอร์ด → เลือกเงื่อนไข → ตรวจสิทธิ์ → ดึงข้อมูล → คำนวณตัวชี้วัด → แสดงผล → เปลี่ยนเงื่อนไขหรือจบ เพิ่มทางไม่มีข้อมูลและโหลดไม่สำเร็จ]

ภาพที่ 3.12 แผนภาพกิจกรรมดูข้อมูลสรุปการใช้งาน

## 3.5 แผนภาพโครงสร้างฐานข้อมูล (ER Diagram)

ฐานข้อมูลเชิงสัมพันธ์ประกอบด้วยตารางหลัก 10 ตาราง ได้แก่ users, bots, documents, bot_documents, conversations, notifications, live_sessions, live_messages, password_reset_tokens และ audit_logs โดยฐานข้อมูลเวกเตอร์สำหรับข้อความเอกสารแยกออกจากตารางเหล่านี้

ความสัมพันธ์หลักมีดังนี้

1. users หนึ่งรายการเป็นเจ้าของ bots และ documents ได้หลายรายการ ผ่าน owner_id
2. bots และ documents มีความสัมพันธ์หลายต่อหลายผ่าน bot_documents ซึ่งใช้ bot_id และ document_id เป็นคีย์หลักร่วม
3. bots หนึ่งรายการมี conversations และ live_sessions ได้หลายรายการ
4. live_sessions หนึ่งรายการมี live_messages ได้หลายข้อความ
5. users หนึ่งรายการมี notifications และ password_reset_tokens ได้หลายรายการ
6. audit_logs อ้างอิง users สองหน้าที่ คือผู้ดำเนินการผ่าน actor_id และผู้ใช้เป้าหมายผ่าน target_user_id โดยทั้งสองคอลัมน์เป็นค่าว่างได้

conversations.session_id เป็นข้อความสำหรับระบุรอบ ไม่ได้ประกาศเป็น Foreign Key ไปยัง live_sessions.id ซึ่งเป็นจำนวนเต็ม การเชื่อมประวัติใช้ข้อมูลบอทและตัวระบุรอบตามตรรกะโปรแกรม จึงไม่ควรวาดเส้น FK ระหว่างคอลัมน์ทั้งสองนี้ ในทำนองเดียวกัน live_sessions.line_user_id ใช้เก็บตัวระบุคู่สนทนาและอาจใช้ค่ารอบจากเว็บไซต์ตามเส้นทางทำงาน ไม่ใช่ FK ไปยัง users.id

[แทรกภาพที่ 3.13: ER Diagram แสดงตารางทั้ง 10 พร้อม PK/FK และ cardinality ตามรายการข้างต้น แสดง audit_logs เชื่อม users สองเส้นพร้อมชื่อบทบาท actor/target คอลัมน์อ้างอิงผู้ใช้ใน audit_logs เป็น optional และแสดงฐานข้อมูลเวกเตอร์แยกต่างหากหากต้องการอธิบายภาพรวม ไม่สร้างตาราง roles เพิ่มเพราะระบบเก็บบทบาทเป็น Enum]

### 3.7.7 หน้าสนทนาบนเว็บไซต์

ประกอบด้วยส่วนเลือกบอท พื้นที่แสดงข้อความ ช่องพิมพ์คำถาม และแหล่งอ้างอิงของคำตอบเมื่อมีข้อมูล ระบบแสดงสถานะระหว่างรอคำตอบ และเสนอการติดต่อผู้ดำเนินงานในกรณีที่ไม่พบข้อมูลเพียงพอ

[แทรกภาพที่ 3.20: แบบหน้าสนทนา แสดงตำแหน่งชื่อบอท คำถาม คำตอบ แหล่งอ้างอิง และช่องพิมพ์]

ภาพที่ 3.20 การออกแบบหน้าสนทนาบนเว็บไซต์

### 3.7.8 รูปแบบข้อความบน LINE OA

การใช้งานผ่าน LINE อาศัยหน้าสนทนาของแอปพลิเคชัน LINE โดย Scopebot กำหนดรูปแบบข้อความตอบกลับและตัวเลือกติดต่อผู้ดำเนินงานตามเส้นทางทำงาน จึงเป็นการออกแบบผลข้อความจากระบบ ไม่ใช่การพัฒนาหน้าจอแอป LINE ขึ้นใหม่

[แทรกภาพที่ 3.21: แบบการแสดงข้อความ LINE OA ใช้บัญชีทดสอบ แสดงข้อความตอบและตัวเลือกติดต่อผู้ดำเนินงาน]

ภาพที่ 3.21 การออกแบบข้อความตอบกลับผ่าน LINE OA

### 3.7.9 หน้ารวมแชทและรับช่วงสนทนา

แสดงรายการรอบสนทนา สถานะการรอ และรายละเอียดข้อความของเรื่องที่เลือก ผู้ดำเนินงานใช้ช่องตอบกลับและปุ่มจบการสนทนาเพื่อจัดการการให้บริการ โดยข้อมูลทุกส่วนต้องอยู่ในขอบเขตบอทที่มีสิทธิ์

[แทรกภาพที่ 3.22: แบบหน้ารวมแชท แสดงรายการด้านข้าง ข้อความ ผู้ส่ง สถานะ และปุ่มจบการสนทนา]

ภาพที่ 3.22 การออกแบบหน้ารวมแชทและรับช่วงสนทนา

### 3.7.10 หน้าประวัติการสนทนา

แสดงรายการบทสนทนาและตัวเลือกบอท พร้อมช่องค้นหา ผู้ใช้เปิดรายละเอียดของแต่ละรอบเพื่อดูข้อความและช่องทางย้อนหลังได้ การแสดงผลต้องรักษาลำดับเหตุการณ์และระบุผู้ส่งให้เข้าใจง่าย

[แทรกภาพที่ 3.23: แบบหน้าประวัติ แสดงตัวเลือกบอท ช่องค้นหา และรายละเอียดรอบจากเว็บไซต์กับ LINE]

ภาพที่ 3.23 การออกแบบหน้าประวัติการสนทนา

### 3.7.11 หน้าแดชบอร์ด

แสดงข้อมูลสรุปการใช้งาน เช่น จำนวนบอท รายการสนทนา สัดส่วนช่องทาง และคิวรอ โดยใช้คำอธิบายตัวเลขให้ตรงกับหน่วยนับ ผู้ใช้สามารถเลือกช่วงเวลาหรือรายละเอียดตามตัวเลือกที่ระบบรองรับได้

[แทรกภาพที่ 3.24: แบบแดชบอร์ด แสดงชื่อรายการตัวชี้วัด ช่วงเวลา และพื้นที่กราฟ ใช้ข้อมูลทดสอบและไม่ตีความตัวเลขการตอบเป็นความถูกต้องเชิงเนื้อหา]

ภาพที่ 3.24 การออกแบบหน้าแดชบอร์ด

การออกแบบทั้งเจ็ดส่วนเชื่อมโยงการทำงานตามวัตถุประสงค์ของโครงงาน ตั้งแต่การเตรียมเอกสาร การให้บริการผ่านเว็บไซต์และ LINE OA ไปจนถึงการตรวจสอบประวัติ โดยผลการพัฒนาและการทดสอบตามการออกแบบนำเสนอในบทที่ 4
