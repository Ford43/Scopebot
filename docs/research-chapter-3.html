บทที่ 3

การวิเคราะห์และการออกแบบระบบ

โครงงานภาคอุตสาหกรรมแชตบอตอัจฉริยะสำหรับสนับสนุนการให้บริการลูกค้าจากข้อมูลในเอกสาร บริษัท โทรคมนาคมแห่งชาติ จำกัด (มหาชน) (NT) เป็นการพัฒนาระบบ Scopebot เพื่อใช้เอกสารเป็นฐานความรู้สำหรับตอบคำถาม รองรับการรับส่งข้อความผ่านเว็บไซต์และ LINE Official Account (LINE OA) และรวบรวมข้อมูลการสนทนาไว้ในระบบเดียวสำหรับตรวจสอบย้อนหลัง

การวิเคราะห์และออกแบบระบบในบทนี้ประกอบด้วยขอบเขตการทำงาน แผนภาพยูสเคส คำอธิบายยูสเคส แผนภาพกิจกรรม การออกแบบฐานข้อมูล พจนานุกรมข้อมูล และการออกแบบส่วนติดต่อผู้ใช้ โดยกำหนดการเข้าถึงข้อมูลตามบทบาทและความเป็นเจ้าของบอท เพื่อให้การจัดการเอกสารและบทสนทนาอยู่ภายในขอบเขตสิทธิ์ของผู้ใช้งาน

3.1 ขอบเขตการทำงานของระบบ

3.1.1 ภาพรวมของระบบ

ระบบแบ่งการทำงานเป็นส่วนติดต่อผู้ใช้ผ่านเว็บไซต์ ส่วนให้บริการข้อมูล และส่วนค้นหาและสร้างคำตอบจากเอกสาร เว็บไซต์พัฒนาด้วย React และ TypeScript โดยใช้ Vite และ Tailwind CSS ส่วนให้บริการข้อมูลพัฒนาด้วย FastAPI และจัดการข้อมูลเชิงสัมพันธ์ผ่าน SQLAlchemy ส่วนตอบคำถามใช้แนวทาง Retrieval-Augmented Generation (RAG) ร่วมกับแบบจำลองภาษาที่เรียกผ่าน Ollama และฐานข้อมูลเวกเตอร์ Chroma หรือ Qdrant ตามการตั้งค่าของบอท

กระบวนการเตรียมความรู้เริ่มจากการนำเข้าเอกสาร อ่านข้อความ แบ่งข้อความเป็นส่วนย่อย และสร้างเวกเตอร์ เมื่อผู้ใช้ส่งคำถาม ระบบค้นหาข้อความในฐานความรู้ของบอทนั้นและใช้หลักฐานประกอบคำตอบ พร้อมตรวจสอบความสอดคล้องของคำตอบกับข้อมูลที่ค้นพบ หากหลักฐานไม่เพียงพอ ระบบแจ้งข้อจำกัดและเสนอช่องทางติดต่อผู้ดำเนินงานตามเงื่อนไขของช่องทางสนทนา

3.1.2 ผู้สมัครและผู้ใช้งานบัญชีทั่วไป

ผู้สมัครสามารถสร้างบัญชีใหม่โดยกรอกอีเมล ชื่อผู้ใช้ และรหัสผ่าน บัญชีใหม่ต้องรอการอนุมัติก่อนเข้าใช้งาน เมื่อได้รับอนุมัติแล้ว ผู้ใช้บทบาท User สามารถจัดการบอทและข้อมูลของตนเองภายในจำนวนบอทที่ได้รับอนุญาต ในโครงงานนี้ใช้คำว่า “ผู้ดูแลบอท” เพื่ออธิบายหน้าที่ของบัญชีที่จัดการบอท โดยไม่ได้หมายถึงบทบาท Admin เสมอไป

1. สมัครสมาชิก — ข้อมูลเข้า ได้แก่ อีเมล ชื่อผู้ใช้ และรหัสผ่าน ผลลัพธ์คือบัญชีใหม่ที่มีสถานะรออนุมัติ

2. เข้าสู่ระบบ — ข้อมูลเข้า ได้แก่ อีเมลและรหัสผ่าน ผลลัพธ์คือสิทธิ์เข้าใช้งานตามสถานะและบทบาทบัญชี

3. จัดการบอท — ข้อมูลเข้า ได้แก่ ชื่อ คำอธิบาย และฐานค้นหาของบอท ผลลัพธ์คือรายการบอทภายใต้บัญชีของตนเอง

4. จัดการเอกสารความรู้ — ข้อมูลเข้า ได้แก่ไฟล์ PDF, DOCX, TXT หรือ CSV และบอทเป้าหมาย ผลลัพธ์คือเอกสารในคลังและฐานความรู้ที่พร้อมเมื่อประมวลผลสำเร็จ

5. สนทนาบนเว็บไซต์ — ข้อมูลเข้า ได้แก่ บอทที่เลือก คำถาม และรอบสนทนา ผลลัพธ์คือคำตอบหรือข้อความแจ้งสถานะ พร้อมประวัติที่เกี่ยวข้อง

6. เชื่อมต่อ LINE OA — ข้อมูลเข้า ได้แก่บอทและข้อมูลช่องทาง LINE ผลลัพธ์คือการตั้งค่าช่องทางสำหรับรับส่งข้อความ

7. รับช่วงสนทนา — ข้อมูลเข้า ได้แก่รอบสนทนาที่รอผู้ดำเนินงานและข้อความตอบกลับ ผลลัพธ์คือข้อความที่บันทึกและการส่งต่อไปยังช่องทางที่เกี่ยวข้อง

8. ตรวจสอบประวัติและภาพรวม — ข้อมูลเข้า ได้แก่บอท รายการสนทนา หรือช่วงเวลาที่เลือก ผลลัพธ์คือประวัติและข้อมูลสรุปภายในขอบเขตสิทธิ์

หน้าสนทนาบนเว็บไซต์ในรุ่นที่ตรวจสอบเป็นหน้าที่ต้องเข้าสู่ระบบและตรวจสิทธิ์ความเป็นเจ้าของบอท จึงไม่ได้กำหนดให้ลูกค้าทั่วไปที่ไม่มีบัญชีเข้าถึงบอทขององค์กรทุกตัวได้ ส่วนผู้สนทนาผ่าน LINE ใช้ตัวระบุผู้ใช้จาก LINE และไม่จำเป็นต้องมีบัญชีในตารางผู้ใช้ของ Scopebot

3.1.3 ผู้ดูแลระบบ Admin และผู้สนับสนุนระบบ Support

Admin และ Support สามารถเข้าถึงส่วนจัดการผู้ใช้งานตามสิทธิ์ที่กำหนด เช่น การพิจารณาบัญชีรออนุมัติ โดย Support ไม่สามารถแก้ไขบัญชี Admin และการเปลี่ยนบทบาทสงวนให้ Admin การจัดการบอท เอกสาร และบทสนทนาของผู้ดูแลบอทแยกจากหน้าที่จัดการผู้ใช้ของแพลตฟอร์ม

1. พิจารณาบัญชีผู้ใช้ — ข้อมูลเข้า ได้แก่บัญชีเป้าหมายและผลการพิจารณา ผลลัพธ์คือสถานะบัญชีที่ปรับปรุงตามสิทธิ์

2. จัดการสถานะและสิทธิ์ — ข้อมูลเข้า ได้แก่สถานะการใช้งาน จำนวนบอทที่อนุญาต หรือบทบาทตามสิทธิ์ผู้ดำเนินการ ผลลัพธ์คือข้อกำหนดบัญชีที่เปลี่ยนแปลงและบันทึกการดำเนินการ

3. ตรวจสอบการบริหารระบบ — Admin ใช้ข้อมูลภาพรวมระบบและบันทึกการดำเนินการประกอบการดูแลแพลตฟอร์ม ขณะที่ข้อมูลบอทและบทสนทนายังคงมีการตรวจสิทธิ์ความเป็นเจ้าของ

คำว่า “ผู้ดำเนินงาน” ในการรับช่วงสนทนาหมายถึงบัญชีที่มีสิทธิ์ดูแลบอทนั้น ไม่ใช่การกำหนดให้บัญชี Support ตอบบทสนทนาของทุกบอทได้

3.1.4 ผู้สนทนาผ่าน LINE OA

ผู้สนทนาสามารถส่งคำถามผ่าน LINE OA ที่เชื่อมกับบอท รับข้อความตอบกลับ และร้องขอติดต่อผู้ดำเนินงานได้ ระบบใช้ข้อมูลเหตุการณ์จาก LINE เพื่อระบุบอทและรอบสนทนา โดยบันทึกข้อความสำหรับการตรวจสอบในระบบกลาง ทั้งนี้ การรวบรวมข้อมูลสองช่องทางไม่ได้หมายถึงการรวมตัวตนผู้ใช้เว็บไซต์กับ LINE เป็นบุคคลเดียวกันโดยอัตโนมัติ

3.1.5 ขอบเขตและเงื่อนไขของข้อมูล

เอกสารความรู้ต้องได้รับอนุญาตให้นำมาใช้งานและมีเนื้อหาที่อ่านได้ การตอบคำถามต้องอาศัยหลักฐานจากเอกสารของบอทที่เกี่ยวข้อง และไม่ใช้คำตอบเดิมของบอทเป็นข้อเท็จจริง การแสดงเลขหน้าอ้างอิงทำได้เมื่อข้อมูลแหล่งอ้างอิงมีเลขหน้า การปรับปรุงเอกสารใช้การสร้างฐานความรู้รุ่นใหม่ก่อนเผยแพร่ โดยการลบหรือแทนที่ข้อมูลมีเงื่อนไขป้องกันการตอบจากความรู้ที่ถูกถอนออก

3.2 แผนภาพยูสเคส (Use Case Diagram)

การออกแบบกำหนดขอบเขตระบบเป็น “Scopebot” และแสดงกิจกรรมที่ผู้ใช้งานภายนอกโต้ตอบกับระบบ โดยแบ่ง Actor ตามหน้าที่ ได้แก่ ผู้สมัคร ผู้ดูแลบอท ผู้ดูแลระบบ Admin ผู้สนับสนุนระบบ Support และผู้สนทนาผ่าน LINE OA ส่วน LINE Platform เป็นระบบภายนอกที่รับส่งเหตุการณ์ข้อความกับ Scopebot ผู้ดำเนินงานรับช่วงสนทนาเป็นหน้าที่ของผู้ดูแลบอทที่มีสิทธิ์เข้าถึงบอทนั้น

กำหนดยูสเคสหลัก 11 รายการดังนี้

1. UC01 สมัครสมาชิก — ผู้สมัคร

2. UC02 เข้าสู่ระบบ — ผู้ดูแลบอท, Admin และ Support

3. UC03 พิจารณาอนุมัติผู้ใช้งาน — Admin และ Support ภายในสิทธิ์

4. UC04 จัดการบอท — ผู้ดูแลบอท

5. UC05 จัดการเอกสารและฐานความรู้ — ผู้ดูแลบอท

6. UC06 ตั้งค่าการเชื่อมต่อ LINE OA — ผู้ดูแลบอท

7. UC07 สนทนาผ่านเว็บไซต์ — ผู้ดูแลบอทหรือผู้ใช้เว็บไซต์ที่มีสิทธิ์ในบอท

8. UC08 สนทนาผ่าน LINE OA — ผู้สนทนาผ่าน LINE OA และ LINE Platform

9. UC09 รับช่วงสนทนาโดยผู้ดำเนินงาน — ผู้ดูแลบอท และผู้สนทนาที่ขอความช่วยเหลือ

10. UC10 ตรวจสอบประวัติการสนทนา — ผู้ดูแลบอท

11. UC11 ดูข้อมูลสรุปการใช้งาน — ผู้ดูแลบอท

3.3 คำอธิบายยูสเคส (Use Case Description)

3.4 แผนภาพกิจกรรม (Activity Diagram)

แผนภาพกิจกรรมแสดงลำดับการทำงานตามยูสเคส โดยแบ่งช่องผู้รับผิดชอบระหว่างผู้ใช้งาน ระบบ Scopebot และระบบภายนอกเมื่อเกี่ยวข้อง ใช้กิจกรรมสำหรับขั้นตอนการกระทำ จุดตัดสินใจสำหรับเงื่อนไข และจุดรวมทางเลือกเมื่อเส้นทางกลับมาดำเนินการร่วมกัน จำนวนกิจกรรมอาจแตกต่างจากจำนวนข้อใน Main Flow แต่ต้องรักษาลำดับ เงื่อนไข และผลลัพธ์ที่กำหนดไว้

[แทรกภาพที่ 3.2: Activity UC01 แบ่งช่องผู้สมัคร/ระบบ ลำดับ เปิดแบบฟอร์ม → กรอกและส่ง → ตรวจข้อมูล → ตัดสินใจผ่านหรือไม่ ทางไม่ผ่านแสดงข้อผิดพลาดและย้อนผ่านจุดรวมก่อนกรอก ทางผ่านแฮชรหัสผ่านและบันทึกบัญชี → แจ้งเตือน → audit log → แสดงผล → สิ้นสุด]

3.5 แผนภาพโครงสร้างฐานข้อมูล (ER Diagram)

ฐานข้อมูลเชิงสัมพันธ์ประกอบด้วยตารางหลัก 10 ตาราง ได้แก่ users, bots, documents, bot_documents, conversations, notifications, live_sessions, live_messages, password_reset_tokens และ audit_logs โดยฐานข้อมูลเวกเตอร์สำหรับข้อความเอกสารแยกออกจากตารางเหล่านี้

ความสัมพันธ์หลักมีดังนี้

1. users หนึ่งรายการเป็นเจ้าของ bots และ documents ได้หลายรายการ ผ่าน owner_id

2. bots และ documents มีความสัมพันธ์หลายต่อหลายผ่าน bot_documents ซึ่งใช้ bot_id และ document_id เป็นคีย์หลักร่วม

3. bots หนึ่งรายการมี conversations และ live_sessions ได้หลายรายการ

4. live_sessions หนึ่งรายการมี live_messages ได้หลายข้อความ

5. users หนึ่งรายการมี notifications และ password_reset_tokens ได้หลายรายการ

6. audit_logs อ้างอิง users สองหน้าที่ คือผู้ดำเนินการผ่าน actor_id และผู้ใช้เป้าหมายผ่าน target_user_id โดยทั้งสองคอลัมน์เป็นค่าว่างได้

conversations.session_id เป็นข้อความสำหรับระบุรอบ ไม่ได้ประกาศเป็น Foreign Key ไปยัง live_sessions.id ซึ่งเป็นจำนวนเต็ม การเชื่อมประวัติใช้ข้อมูลบอทและตัวระบุรอบตามตรรกะโปรแกรม จึงไม่ควรวาดเส้น FK ระหว่างคอลัมน์ทั้งสองนี้ ในทำนองเดียวกัน live_sessions.line_user_id ใช้เก็บตัวระบุคู่สนทนาและอาจใช้ค่ารอบจากเว็บไซต์ตามเส้นทางทำงาน ไม่ใช่ FK ไปยัง users.id

[แทรกภาพที่ 3.13: ER Diagram แสดงตารางทั้ง 10 พร้อม PK/FK และ cardinality ตามรายการข้างต้น แสดง audit_logs เชื่อม users สองเส้นพร้อมชื่อบทบาท actor/target คอลัมน์อ้างอิงผู้ใช้ใน audit_logs เป็น optional และแสดงฐานข้อมูลเวกเตอร์แยกต่างหากหากต้องการอธิบายภาพรวม ไม่สร้างตาราง roles เพิ่มเพราะระบบเก็บบทบาทเป็น Enum]

3.7 การออกแบบหน้าต่างโปรแกรม (User Interface)

การออกแบบส่วนติดต่อผู้ใช้แบ่งตามงานที่ผู้ใช้ต้องดำเนินการ โดยแสดงเมนูตามบทบาท ให้ข้อมูลสถานะและข้อผิดพลาดอยู่ใกล้กิจกรรมที่เกี่ยวข้อง และใช้หน้าประวัติสำหรับตรวจสอบผลย้อนหลัง ภาพในส่วนนี้ควรเป็นแบบร่างหน้าจอหรือภาพหน้าจอที่มีข้อมูลทดสอบ ส่วนผลใช้งานจริงและผลการทดสอบนำเสนอในบทที่ 4

3.7.1 หน้าสมัครสมาชิก

ประกอบด้วยช่องอีเมล ชื่อผู้ใช้ รหัสผ่าน และปุ่มสมัคร ระบบแสดงข้อผิดพลาดเมื่อข้อมูลไม่ผ่านเงื่อนไข และแสดงข้อความให้รอการอนุมัติเมื่อสร้างบัญชีสำเร็จ

[แทรกภาพที่ 3.14: แบบหน้าสมัครสมาชิก แสดงช่องกรอก ปุ่มสมัคร และพื้นที่ข้อความแจ้งผล ใช้ภาพที่ไม่มีข้อมูลส่วนบุคคลจริง]

ภาพที่ 3.14 การออกแบบหน้าสมัครสมาชิก

3.7.2 หน้าเข้าสู่ระบบ

[แทรกภาพที่ 3.15: แบบหน้าเข้าสู่ระบบ แสดงตำแหน่งช่องกรอกและข้อความสถานะ]

ภาพที่ 3.15 การออกแบบหน้าเข้าสู่ระบบ

3.7.3 หน้าจัดการผู้ใช้งาน

แสดงรายการบัญชีพร้อมสถานะการอนุมัติและการใช้งาน ผู้มีสิทธิ์เลือกบัญชีเพื่อดำเนินการได้ โดยตัวเลือกต้องสอดคล้องกับสิทธิ์ Admin และ Support รวมถึงการจำกัดการเปลี่ยนบทบาทและการแก้ไขบัญชี Admin

[แทรกภาพที่ 3.16: แบบหน้าจัดการผู้ใช้งาน แสดงบัญชีทดสอบที่รออนุมัติและปุ่มดำเนินการตามสิทธิ์]

ภาพที่ 3.16 การออกแบบหน้าจัดการผู้ใช้งาน

3.7.4 หน้าจัดการบอท

[แทรกภาพที่ 3.17: แบบรายการบอทและแบบฟอร์มสร้างบอท จัดเป็นภาพย่อยหากจำเป็น]

แสดงข้อมูลสรุปการใช้งาน เช่น จำนวนบอท รายการสนทนา สัดส่วนช่องทาง และคิวรอ โดยใช้คำอธิบายตัวเลขให้ตรงกับหน่วยนับ ผู้ใช้สามารถเลือกช่วงเวลาหรือรายละเอียดตามตัวเลือกที่ระบบรองรับได้

[แทรกภาพที่ 3.24: แบบแดชบอร์ด แสดงชื่อรายการตัวชี้วัด ช่วงเวลา และพื้นที่กราฟ ใช้ข้อมูลทดสอบและไม่ตีความตัวเลขการตอบเป็นความถูกต้องเชิงเนื้อหา]
