# Authentication audit and throttling

Apply Alembic revision `007_authentication_security` through the normal deployment process **before starting the new application workers**. This change does not run a migration automatically. The migration only adds `login_throttles` and `revoked_tokens`; existing users, audit history and JWTs remain intact. Roll out all authentication workers together: an older worker does not enforce revocations or login limits.

Each normalized limiter key (trimmed, case-folded email) permits four failed attempts; the fifth failure within the preceding 15 minutes starts a five-minute cooldown and returns HTTP 429 with `Retry-After` seconds. A separate source-IP limit starts a five-minute cooldown at 30 failures within 15 minutes, covering attempts distributed over many accounts. Requests during either cooldown do not verify passwords, add failures, or extend the deadline. After cooldown the corresponding failure budget restarts; successful login clears only its account budget. Inactive and unapproved accounts use the same generic failure response as invalid credentials. Unknown accounts still perform password verification and appear under a pseudonymous HMAC identifier in the audit trail.

Limits persist across process restarts and workers. PostgreSQL atomic upserts acquire account/IP rows in deterministic order and retain row locks through verification and the audit/limit commit. SQLite uses the same write-first upsert to serialize transactions. Authentication state and audit commits fail closed. The server clock drives cooldowns; keep application worker clocks synchronized.

IP comes only from the ASGI `request.client`, never directly from request headers. Configure Uvicorn's trusted proxy addresses (`--forwarded-allow-ips`) for the actual reverse proxy only; do not trust arbitrary forwarding sources. Restrict direct access to the backend when behind a proxy. Without correctly configured proxy trust, all requests may share the proxy IP and its limit. Shared corporate NAT users also share the 30-failure IP budget.

Account lookup retains the existing case-sensitive email identity; case variants share a limiter budget but never select each other's accounts.

New JWTs contain a unique `jti`, so simultaneous logins are separate. Logout stores only the SHA-256 hash of the verified token identity (signed input plus canonical signature bytes) and its expiry; every authenticated request checks that denylist. Equivalent signature encodings, including padding variants, share the same revocation identity. Legacy signed JWTs with `sub` and `exp` also work and can be revoked. Previously issued identical legacy tokens represent the same token, so revoking one invalidates all copies. Already running requests are not cancelled by logout. Logout retries are idempotent, including when the response is lost after commit; only the first revocation produces a `logout` event. Browser logout retains credentials and shows an error if the server cannot confirm completion, allowing retry. Expired/invalid tokens may be cleared after HTTP 401.

Audit events are `login_success`, `login_failed` (including the threshold-crossing attempt), `login_throttled` (requests made during cooldown), and `logout`. They use database timestamps, displayed in Asia/Bangkok to the second. Admin-only filters combine event, account name, inclusive Thai calendar dates and pagination. Passwords and bearer tokens are never written to these audit events. Known accounts use their username; unknown submitted emails and source IPs are represented only by keyed hashes in throttle state, not raw values.

Operational retention: audit and throttle rows are persistent and require an organization-defined retention policy. Expired denylist rows may be removed only after `expires_at`; inactive throttle rows may be removed after at least 15 minutes beyond `updated_at` and after `blocked_until` has elapsed. Perform cleanup in bounded batches with the same row-locking discipline; do not delete active state or reset the tables to resolve errors. No retention job is installed by this feature. Changing `SECRET_KEY` invalidates JWTs and resets the effective pseudonymous limiter keys. Downgrading removes enforcement tables and loses their state; do not downgrade while these workers are serving traffic.

Verification includes disposable SQLite databases and HTTP tests, including concurrency. Run the opt-in PostgreSQL integration check from the repository root with `.\.venv\Scripts\python.exe -m test.run_auth_postgres --run`. It uses the configured PostgreSQL credentials to create a uniquely named `scopebot_auth_test_*` database, starts two hidden Uvicorn processes hosting the production authentication router, and removes only that disposable database afterward. The configured role needs permission to create/drop databases. It does not start the full application or its RAG services, and does not create accounts in the configured application database.

The PostgreSQL check covers the 006-to-007 migration, concurrent account/IP thresholds, unchanged cooldown deadlines, restart persistence, cross-worker token validation and revocation, and concurrent idempotent logout with exactly one audit event. Cooldown expiry is simulated by changing only the disposable database deadline; active-cooldown and restart checks use the real clock. It bootstraps a revision-006 schema from model metadata and stamps 006 before applying 007: the historical migration 001 currently fails on a fresh PostgreSQL database with `DuplicateObject` because enum types are created twice. This check therefore does not validate a clean-install migration chain or full application/proxy deployment.
